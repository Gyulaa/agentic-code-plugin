# Save

Write down what the next session needs, in the project's own note layout (the project `CLAUDE.md` says where; the defaults come from `project-setup`).

1. **State file** (`STATE.md`): rewrite it to stay **one page**. Keep: what the project is (one line), the current state of each active thread, open PRs and branches, what is blocked and on whom, the next step. Remove what is finished and no longer useful; history belongs in the session log or git, not here. Date it (`YYYY-MM-DD`, from the system clock).
2. **Decisions:** an entry in the decision log (`docs/decisions.md`, or one file per decision in larger projects) only for what **guides future work**: a rule, a direction, or a reason without which the question would come up again (reversing it would be costly or confusing if the reason were unknown). Write the date, the decision, why, what it affects, and in a team who decided. A changed decision is updated, not duplicated. These are **not** decisions: a one-off step (merging a branch, deleting a function, rewording a text), a bug fix, a routine dependency update, anything an accepted decision already covers. They belong in the session log, the state file or the PR.
3. **Bugs:** every bug found but not fixed gets an entry in the bug list (`docs/bugs.md` or one file per bug): ID (the next free number), severity (critical / high / medium / low), status (open / in progress / PR open / fixed), one line, where it is in the code, and `origin:` if it came from an earlier change. A default branch that does not build is a critical bug. **A missing test is not a bug:** a bug is wrong behaviour, a missing test is test debt (`scripts/test_debt.py add`, where the project has it, or the project's own place for it).
4. **Session log** (only if the project keeps one, typically larger or team projects): `docs/sessions/YYYY-MM-DD-short-topic.md` with what was done, what was created or changed, and links to the decisions and bugs above.
5. **Archive** (only where the project keeps one file per item, or a separate archive folder): move the closed items in one pass, keeping their file names: fixed bugs, rejected or superseded decisions, session logs older than 30 days. An accepted decision stays where it is. Never delete a decision or a bug, only change its status and move it. At most 20 files in one pass; if there are more, tell the user and let them decide.
6. **What's new** (if the README has a "What's new" section that works as a team news feed, typically in team projects): if this session changed something a teammate must know to work correctly (a new rule or workflow, a new command or tool, a decision that changes how people work, a breaking change), add one dated line at the top, written for a person who was away: what changed and what to do differently, with a link to the decision or note. If the topic already has a line, update that line instead of writing a second one. Routine fixes don't go here. Keep at most 5 entries, none older than 7 days; what falls out moves unchanged to the archive, where there is one. If the change makes another README section untrue, fix that section too. A section that is a release log (one line per released version, as in a tool's own README) is not a news feed: leave it alone.
7. **Friction:** if something was slow or failed repeatedly this session, add one line to the state file's "Friction" list (create it if missing): what, how often, rough cost. `/agentic-code:improve-workflow` works from this list.
8. **Never** write a secret, token, password or personal data into notes. Never paste whole files; link to them.
9. Show the user, in a few lines, what you wrote and where. **Commit only if the user asks** or the project's rules say notes are committed automatically; pushing still needs permission (`git-workflow`).

$ARGUMENTS, if given, is the user's own summary of the session: use it as the starting point.
